Documentação Técnica: TerraBlender e Adição de Novos Biomas no Overworld com NeoForge 1.21.11

Este documento descreve uma arquitetura generalizada para integração de TerraBlender em projetos NeoForge 1.21.11, focada em adição de biomas no Overworld com previsibilidade, depuração robusta e manutenção de longo prazo.

Visão Geral

Em NeoForge 1.21.11, a geração de biomas no Overworld é resolvida por um sistema climático multi-dimensional (temperatura, umidade, continentalidade, erosão, weirdness e offset). Para inserir um novo bioma de forma controlada, é necessário decidir em qual camada atuar: modificação de listas de biomas, inserção de regiões climáticas ou datapack puro. TerraBlender atua no nível de distribuição climática, oferecendo um ponto de integração mais próximo da seleção final do bioma.

O que é TerraBlender

TerraBlender é uma biblioteca de worldgen que permite registrar regiões e mapear biomas para pontos de clima (Climate.ParameterPoint), influenciando diretamente a resolução do bioma durante a geração do mundo. Em vez de apenas anexar um bioma a listas existentes, ele permite definir com precisão em quais condições climáticas seu bioma deve surgir.

Por que usar TerraBlender em vez de neoforge:add_biomes

  • Controle climático explícito: TerraBlender permite mapear ranges de clima de forma declarativa e auditável.

  • Previsibilidade: É possível ajustar densidade e distribuição com weight de região e granularidade dos ParameterPoints.

  • Escalabilidade: Bom para múltiplos biomas e famílias de biomas sem depender apenas de seletores genéricos.

  • Menor ambiguidade: Evita conflitos de comportamento quando vários sistemas tentam inserir o mesmo bioma por caminhos diferentes.

Diferença entre BiomeModifier, TerraBlender Region e Datapack puro

Abordagem Camada de atuação Vantagem principal Limitação principal
BiomeModifier Ajuste de comportamento de biomas e hooks de worldgen Ótimo para adicionar features, spawns e ajustes em biomas já existentes Não é o mecanismo ideal para modelar distribuição climática detalhada de novos biomas
TerraBlender Region Distribuição climática e seleção de biomas Permite mapear ParameterPoints e controlar inserção no Overworld em nível estrutural Exige entendimento da pipeline de climate/multi-noise
Datapack puro Dados de worldgen, biome, features e superfícies Forte desacoplamento de código e boa interoperabilidade Sem integração programática de região climática do TerraBlender por si só

Como TerraBlender integra com Climate / MultiNoise

Internamente, o sistema de seleção de bioma consulta espaços climáticos. TerraBlender injeta novos mapeamentos de bioma para pontos climáticos (ParameterPoints) dentro de regiões registradas. Na prática, você define ranges para cada dimensão climática e associa esses ranges ao ResourceKey do bioma. O resolvedor de biomas então passa a considerar esses pontos durante a escolha final.

Arquitetura Interna do TerraBlender

Region

Classe base para declarar uma região customizada e informar tipo/dimensão e weight. Também é o ponto onde você adiciona mapeamentos climáticos para biomas.

RegionType

Define o domínio de aplicação da região. Para este cenário, use OVERWORLD para atuar na seleção de biomas do mundo principal.

Regions.register(...)

Registro global da instância de Region. Sem esse passo, sua região nunca entra na pipeline de worldgen.

addBiomes(...)

Método no qual a região popula o builder de clima com ParameterPoints e chaves de bioma. Este é o núcleo da distribuição.

Climate.ParameterPoint

Estrutura que modela os eixos climáticos e define onde um bioma pode aparecer. Ranges muito estreitos reduzem chance prática; ranges muito largos aumentam incidência.

Weight da Region

O weight afeta prioridade/força relativa da região no conjunto total. Não é um "percentual direto" de spawn, mas altera a influência da região no processo.

Como TerraBlender intercepta a seleção de biomas

TerraBlender injeta seus pontos climáticos na fonte de parâmetros do Overworld durante a preparação de worldgen. Assim, na resolução final de multi-noise, seus biomas entram no universo de candidatos.

Pipeline completo: Boot → Registro → Worldgen → Climate → Resolução final do Bioma

  1. Boot: Inicialização da aplicação e carregamento de registries.

  2. Registro: Sua Region é registrada (geralmente em common setup com enqueueWork).

  3. Worldgen: O motor prepara fontes de bioma e regras.

  4. Climate: ParameterPoints são avaliados contra valores climáticos locais.

  5. Resolução final: O sistema escolhe o ResourceKey de bioma mais adequado para aquele ponto do mundo.

Implementação Passo a Passo

Classe Region (Overworld)

package com.example.mod.worldgen.terrablender;

import com.mojang.datafixers.util.Pair;
import net.minecraft.resources.ResourceKey;
import net.minecraft.resources.ResourceLocation;
import net.minecraft.world.level.biome.Biome;
import net.minecraft.world.level.biome.Climate;
import terrablender.api.ParameterUtils;
import terrablender.api.Region;
import terrablender.api.RegionType;

public class ModRegion extends Region {
    public static final ResourceKey<Biome> CUSTOM_BIOME = ResourceKey.create(
        net.minecraft.core.registries.Registries.BIOME,
        ResourceLocation.fromNamespaceAndPath("examplemod", "custom_overworld_biome")
    );

    public ModRegion(ResourceLocation name, int weight) {
        super(name, RegionType.OVERWORLD, weight);
    }

    @Override
    public void addBiomes(Registry<Biome> registry, Consumer<Pair<Climate.ParameterPoint, ResourceKey<Biome>>> mapper) {
        this.addModifiedVanillaOverworldBiomes(mapper, builder -> {
            Climate.ParameterPoint point = new Climate.ParameterPoint(
                ParameterUtils.Temperature.NEUTRAL.parameter(),
                ParameterUtils.Humidity.HUMID.parameter(),
                ParameterUtils.Continentalness.INLAND.parameter(),
                ParameterUtils.Erosion.EROSION_2.parameter(),
                ParameterUtils.Weirdness.MID_SLICE_NORMAL_ASCENDING.parameter(),
                Climate.Parameter.span(0.0F, 0.0F),
                0L
            );
            builder.add(point, CUSTOM_BIOME);
        });
    }
}

Registro via FMLCommonSetupEvent + enqueueWork

package com.example.mod.worldgen.terrablender;

import net.minecraft.resources.ResourceLocation;
import net.neoforged.bus.api.SubscribeEvent;
import net.neoforged.fml.common.EventBusSubscriber;
import net.neoforged.fml.event.lifecycle.FMLCommonSetupEvent;
import terrablender.api.Regions;

@EventBusSubscriber(bus = EventBusSubscriber.Bus.MOD, modid = "examplemod")
public class ModTerrablenderBootstrap {

    @SubscribeEvent
    public static void onCommonSetup(FMLCommonSetupEvent event) {
        event.enqueueWork(() -> {
            Regions.register(new ModRegion(
                ResourceLocation.fromNamespaceAndPath("examplemod", "overworld_region"),
                4
            ));
        });
    }
}

Controle de Raridade

Weight vs raridade prática

Weight altera influência regional, mas a raridade observada depende da interseção entre weight, ranges climáticos e competição com outros biomas. Sempre valide por amostragem em múltiplas seeds.

Ranges climáticos amplos vs estreitos

  • Amplos: maior probabilidade de aparição, porém menor identidade ecológica.

  • Estreitos: bioma mais "especializado", porém risco alto de quase nunca aparecer.

Estratégia TEST vs PROD

Em TEST, use weight maior e ranges mais amplos para confirmar integração rápida. Em PROD, reduza gradualmente até atingir distribuição desejada.

Como evitar bioma impossível

  1. Evite ranges extremos simultâneos em todos os eixos.

  2. Não combine erosão/continentalidade incompatíveis com o perfil desejado.

  3. Teste em seeds distintas e com distância alta de exploração.

Surface Rules (avançado, opcional)

Quando usar SurfaceRuleManager

Use quando o bioma precisa de comportamento de superfície específico (bloco de topo/subsolo) que não pode ser adequadamente representado apenas por JSON de biome e features.

Exemplo simples de regra custom

// Pseudocódigo ilustrativo
SurfaceRuleManager.addSurfaceRules(
    SurfaceRuleManager.RuleCategory.OVERWORLD,
    "examplemod",
    100,
    SurfaceRules.sequence(
        SurfaceRules.ifTrue(
            SurfaceRules.isBiome(ModRegion.CUSTOM_BIOME),
            SurfaceRules.state(ModBlocks.CUSTOM_TOPSOIL.defaultBlockState())
        )
    )
);

Features e Colocação

Pipeline recomendado:

  1. configured_feature: define o que gerar (árvore, patch, ore, estrutura vegetal).

  2. placed_feature: define como/onde/frequência (modificadores de placement).

  3. neoforge:add_features: injeta placed_feature em etapa de decoração apropriada.

Não misture neoforge:add_biomes com TerraBlender para o mesmo bioma, pois você cria duas rotas concorrentes de inserção. Isso pode causar distribuição imprevisível, duplicidade lógica e dificuldade de depuração.

Debug Profissional

Checklist completo

  • Confirmar que Regions.register(...) foi executado no setup comum.

  • Confirmar que o ResourceKey<Biome> aponta para um JSON existente e válido.

  • Verificar logs de carregamento de datapack/registry sem erros silenciosos.

  • Gerar mundo com seed nova após cada ajuste crítico.

  • Testar em modo desenvolvimento sem caches antigos de mundo.

Problemas comuns

Erro observado Causa provável Solução recomendada
Bioma nunca aparece Ranges climáticos estreitos demais ou key incorreta Ampliar ranges temporariamente, validar key/namespace/path e repetir teste com seed nova
Crash em carregamento de worldgen JSON inválido em biome/feature ou referência inexistente Validar JSON, checar logs e conferir ordem de registro de objetos
Distribuição excessiva do bioma Weight alto somado a clima amplo Reduzir weight e restringir pelo menos dois eixos climáticos
Comportamento inconsistente entre mundos Comparação entre seeds distintas sem protocolo Padronizar matriz de testes por seed, distância e tempo de exploração
Features não aparecem no bioma placed_feature não injetada na etapa correta Revisar cadeia configured_feature → placed_feature → biome modifier de features

Boas Práticas

Arquitetura escalável

Separe bootstrap de registro, definição de região, registros de biome e pipeline de features em módulos independentes.

Separação por entries

Mantenha cada entry de biome/feature em arquivo dedicado para facilitar diff, revisão e rollback.

Evitar ranges extremos

Prefira ranges progressivos validados por telemetria de teste em vez de ajustes radicais de uma vez.

Perfil de teste

Use perfil de desenvolvimento com weight temporário alto, logging mais verboso e sementes de benchmark fixas.

Technical Documentation: TerraBlender and Adding New Overworld Biomes with NeoForge 1.21.11

This document describes a generalized architecture for TerraBlender integration in NeoForge 1.21.11 projects, focused on adding Overworld biomes with predictability, robust debugging, and long-term maintainability.

Overview

In NeoForge 1.21.11, Overworld biome generation is resolved by a multi-dimensional climate system (temperature, humidity, continentalness, erosion, weirdness, and offset). To insert a new biome in a controlled way, you must choose the layer where you act: biome list modification, climate-region injection, or pure datapack. TerraBlender operates at climate distribution level, offering an integration point closer to final biome resolution.

What TerraBlender Is

TerraBlender is a worldgen library that lets you register regions and map biomes to climate points (Climate.ParameterPoint), directly influencing biome resolution during world generation. Instead of only appending a biome to existing lists, it lets you define precisely under which climate conditions your biome should appear.

Why Use TerraBlender Instead of neoforge:add_biomes

  • Explicit climate control: TerraBlender lets you map climate ranges declaratively and in an auditable way.

  • Predictability: You can tune density and spread through region weight and ParameterPoint granularity.

  • Scalability: Strong fit for multiple biomes and biome families without relying only on generic selectors.

  • Lower ambiguity: Avoids behavior conflicts when multiple systems try to insert the same biome through different paths.

Difference Between BiomeModifier, TerraBlender Region, and Pure Datapack

Approach Layer of operation Main advantage Main limitation
BiomeModifier Biome behavior adjustment and worldgen hooks Great for adding features, spawns, and tweaks to existing biomes Not the ideal mechanism to model detailed climate distribution of new biomes
TerraBlender Region Climate distribution and biome selection Allows ParameterPoint mapping and structural Overworld insertion control Requires understanding of climate/multi-noise pipeline
Pure datapack Worldgen, biome, features, and surface data Strong code decoupling and good interoperability No TerraBlender climate-region programmatic integration by itself

How TerraBlender Integrates with Climate / MultiNoise

Internally, the biome selection system queries climate spaces. TerraBlender injects new biome mappings to climate points (ParameterPoints) inside registered regions. In practice, you define ranges for each climate dimension and bind those ranges to the biome ResourceKey. The biome resolver then considers those points during final selection.

TerraBlender Internal Architecture

Region

Base class used to declare a custom region and define target type/dimension plus weight. It is also where you add biome-climate mappings.

RegionType

Defines the region application domain. For this scenario, use OVERWORLD to affect main-world biome selection.

Regions.register(...)

Global registration of the Region instance. Without this step, your region never enters worldgen pipeline.

addBiomes(...)

Method where region fills climate builder with ParameterPoints and biome keys. This is the distribution core.

Climate.ParameterPoint

Structure that models climate axes and defines where a biome can appear. Too narrow ranges reduce practical chance; too wide ranges increase incidence.

Region Weight

Weight affects relative region influence in the overall set. It is not a direct spawn percentage, but it changes regional influence in processing.

How TerraBlender Intercepts Biome Selection

TerraBlender injects climate points into Overworld parameter source during worldgen preparation. Therefore, in final multi-noise resolution, your biomes become part of candidate set.

Full Pipeline: Boot → Registration → Worldgen → Climate → Final Biome Resolution

  1. Boot: Application initialization and registry loading.

  2. Registration: Your Region is registered (usually in common setup through enqueueWork).

  3. Worldgen: Engine prepares biome sources and rules.

  4. Climate: ParameterPoints are evaluated against local climate values.

  5. Final resolution: System chooses best biome ResourceKey for that world point.

Rarity Control

Weight vs practical rarity

Weight changes regional influence, but observed rarity depends on intersection between weight, climate ranges, and competition with other biomes. Always validate by sampling across multiple seeds.

Wide vs narrow climate ranges

  • Wide: higher appearance probability, but lower ecological identity.

  • Narrow: more specialized biome, but high risk of near-zero appearance.

TEST vs PROD strategy

In TEST, use higher weight and wider ranges for quick integration confirmation. In PROD, gradually reduce until desired distribution is reached.

How to avoid an impossible biome

  1. Avoid simultaneous extreme ranges on all axes.

  2. Do not combine erosion/continentalness values incompatible with intended profile.

  3. Test on different seeds and with high exploration distance.

Surface Rules (advanced, optional)

When to use SurfaceRuleManager

Use it when biome needs specific surface behavior (top/sub blocks) that cannot be represented adequately only by biome JSON and features.

Features and Placement

Recommended pipeline:

  1. configured_feature: defines what to generate (tree, patch, ore, vegetation structure).

  2. placed_feature: defines how/where/frequency (placement modifiers).

  3. neoforge:add_features: injects placed_feature at appropriate decoration step.

Do not mix neoforge:add_biomes with TerraBlender for the same biome, because that creates two competing insertion routes. This can cause unpredictable distribution, logical duplication, and harder debugging.

Professional Debugging

Complete checklist

  • Confirm Regions.register(...) ran during common setup.

  • Confirm ResourceKey<Biome> points to an existing valid JSON.

  • Inspect datapack/registry loading logs for non-obvious errors.

  • Create a new-seed world after every critical change.

  • Test in development mode without stale world caches.

Common problems

Observed error Likely cause Recommended solution
Biome never appears Climate ranges too narrow or wrong key Temporarily widen ranges, validate key/namespace/path, and retest with new seed
Crash on worldgen load Invalid biome/feature JSON or missing reference Validate JSON, inspect logs, and confirm object registration order
Biome appears too often High weight plus wide climate windows Reduce weight and constrain at least two climate axes
Inconsistent behavior between worlds Different seeds compared without protocol Standardize a test matrix by seed, distance, and exploration time
Features do not appear in biome placed_feature not injected at correct stage Review configured_feature → placed_feature → feature biome modifier chain

Best Practices

Scalable architecture

Separate registration bootstrap, region definition, biome registrations, and feature pipeline into independent modules.

Separation by entries

Keep each biome/feature entry in dedicated files for easier diffs, review, and rollback.

Avoid extreme ranges

Prefer progressive ranges validated by test telemetry instead of radical one-shot tuning.

Test profile

Use a development profile with temporarily high weight, more verbose logging, and fixed benchmark seeds.
